# Инструкции для AI-агентов

## Обязательный порядок работы

Перед изменением кода:

1. Прочитай `ARCHITECTURE.md` и `.opencode/instructions/architecture.md`.
2. Прочитай `.opencode/instructions/java-style.md`.
3. Если задача затрагивает тесты — прочитай `.opencode/instructions/testing.md`.
4. Если задача затрагивает БД, миграции или JPA — прочитай `.opencode/instructions/database.md`.
5. Если задача затрагивает HTTP API — прочитай `.opencode/instructions/api-contracts.md`.
6. Если задача затрагивает безопасность, аутентификацию или авторизацию — прочитай `.opencode/instructions/security.md`.

## Приоритет инструкций

При конфликте правил применяй следующий порядок:

1. Явные требования пользователя для текущей задачи.
2. Локальный `AGENTS.md` ближайшего затронутого модуля.
3. Корневой `AGENTS.md`.
4. `ARCHITECTURE.md` для архитектурных, технологических и проектных решений.
5. Тематические файлы из `.opencode/instructions/`.
6. Существующие соглашения и паттерны кода в модуле.

Если пользовательское требование создаёт риск потери данных, нарушения безопасности,
несовместимого публичного изменения или некорректной миграции, сначала укажи риск
и предложи безопасный вариант реализации.

## Общие правила

- Выполнять разработку в ветке `develop`.
- Вносить изменения в `master` только через слияние завершенной работы из `develop`.
- Язык проекта: Java 21.
- Основной фреймворк: Spring Boot 4.1.0 согласно `ARCHITECTURE.md`; обновление с текущей версии выполняется отдельной проверяемой задачей.
- После изменений запускать релевантные Gradle-задачи.
- Использовать Java toolchain, заданный в `build.gradle`.
- Сборка и проверка: `./gradlew verify`.
- Перед завершением выполни релевантные тесты и сообщи точные команды и их результат.
- Не изменяй публичные API, схему БД, зависимости и конфигурацию CI без явного обоснования в результате работы.
- Не добавляй зависимости, если задачу можно решить средствами JDK или уже подключённых библиотек.
- Не меняй сгенерированные файлы.
- Если требования противоречат друг другу или информации недостаточно, остановись и задай уточняющий вопрос.
- Перед изменениями изучать затрагиваемые код и конфигурацию.
- Сохранять изменения минимальными и соответствующими существующей архитектуре.
- Не добавлять секреты, локальные файлы IDE и результаты сборки в Git.
- Перед коммитом проверять `git status` и состав изменений.
- Если задача явно соответствует шагу плана разработки из `ARCHITECTURE.md`, после успешной реализации, обязательных проверок и требуемого code review агент обязан оформить результат и создать коммит в ветке `develop`.
- Не оформляй запись в `REPORT.md` и не создавай коммит для незавершённого шага, при проваленных либо не выполненных обязательных проверках, нерешённых критичных замечаниях code review, работе не в `develop` или конфликтующих посторонних изменениях в тех же файлах.
- Перед таким коммитом создай prompt, добавь запись в `REPORT.md`, проверь `git status`, `git diff` и историю коммитов; в индекс включай только файлы текущего шага.

## Документирование

- Фиксировать архитектурно значимые решения в `ARCHITECTURE.md`.
- Для завершённого шага плана разработки из `ARCHITECTURE.md` перед обязательным commit создай в `promts/` файл `<название-коммита>.md` и заполни его текстом задания, на основе которого выполнена работа.
- Для завершённого шага плана разработки из `ARCHITECTURE.md` перед обязательным commit добавь в `REPORT.md` запись; номер шага продолжает сквозную нумерацию внутри `REPORT.md`. Используй формат:
```markdown
### Шаг <номер_шага_согласно_сквозной_нумерации_шагов_внутри_REPORT.md>
<Описание_реализованного_шага_из_плана_разработки_файла_ARCHITECTURE.md>

[Промт.](ссылка_на_файл_промта_внутри_директории_promts)

Данная запись сгенерирована агентом.
```

## Локальные инструкции

- При работе в подкаталогах учитывай ближайший `AGENTS.md`.
- Локальные инструкции уточняют правила корня, но не отменяют критичные требования по безопасности, тестированию и совместимости без явного указания пользователя.
