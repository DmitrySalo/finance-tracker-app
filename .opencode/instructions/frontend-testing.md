# Frontend testing

## Назначение

Используй Vitest и Testing Library для быстрых unit и component/integration тестов React-приложения. Тестируй наблюдаемое пользовательское поведение и публичные контракты модулей, а не внутреннее устройство компонентов.

## Выбор уровня теста

- Unit-тесты подходят для чистых formatter, validators, сериализации query-параметров, преобразований DTO и изолированной бизнес-логики.
- Component/integration тесты покрывают формы, маршрутизацию, loading, empty, error и success states, а также взаимодействие feature-компонента с API-клиентом и TanStack Query.
- E2E-тесты добавляй только для ключевых сквозных сценариев, когда Playwright уже настроен в проекте. Не заменяй ими быстрые component-тесты.
- Для исправленного дефекта добавь регрессионный тест на самом малом уровне, который достоверно воспроизводит проблему.

## Vitest и Testing Library

- Располагай тест рядом с кодом под именем `*.test.ts` или `*.test.tsx`.
- Используй `render`, `screen` и запросы по роли, label и доступному имени. Приоритет: `getByRole`, `getByLabelText`, `getByText`; не ищи элементы по CSS-классам, `data-testid` или структуре DOM, если доступный запрос применим.
- Действуй как пользователь: вводи значения и нажимай нативные элементы. Не вызывай component props, приватные функции или методы реализации напрямую.
- Для асинхронно появляющихся элементов применяй `findBy*` или `waitFor` вокруг assertion. Не используй `Thread.sleep`, произвольные задержки и увеличенные timeout как синхронизацию.
- Очищай глобальное состояние после каждого сценария: mocks, in-memory session, history, query cache и изменённые browser API.
- Для пользовательских событий предпочитай установленный в проекте инструмент. Не добавляй библиотеку только ради тестов без необходимости.

## Моки и API-контракты

- Мокай внешние границы: `fetch`, browser API, время и сетевые сбои. Не мокай React, Testing Library, простые типы и собственную чистую логику.
- Проверяй method, URL, query-параметры и существенное body исходящего запроса. Ответы моков должны соответствовать реальному API-контракту из `ARCHITECTURE.md`.
- Покрывай успешный сценарий, client validation, server validation или conflict, network error и authorization failure, когда они релевантны изменению.
- Для mutation проверяй блокировку повторной отправки, отображение результата и корректное обновление либо invalidation server state.
- Не используй реальные сервисы, секреты, production-данные или неограниченный доступ к сети.

## Доступность и адаптивность

- Проверяй доступные имена кнопок, labels полей, текстовые ошибки и статусы, важные для screen reader.
- Не проверяй CSS-классы. Для адаптивных представлений проверяй наблюдаемый вариант интерфейса и, если требуется, настрой состояние viewport детерминированно с обязательным восстановлением после теста.
- Для таблиц, диаграмм и цветовых индикаторов проверяй доступную текстовую альтернативу, пустое состояние и безопасное сообщение об ошибке.

## Качество тестов

- Каждый тест проверяет один понятный сценарий и использует Arrange-Act-Assert.
- Название теста описывает условие, действие и ожидаемый результат.
- Фикстуры должны быть синтетическими, минимальными и читаемыми; меняй только данные, существенные для сценария.
- Тесты независимы от порядка запуска, локали, часового пояса, текущего времени и состояния машины.
- Перед завершением выполни как минимум тесты затронутого файла, затем релевантные `npm run lint`, `npm run test` и `npm run build`; в результате укажи точные команды и их итог.
