# Frontend style guidelines

## Технологический контекст

Frontend разрабатывается на React и TypeScript согласно `ARCHITECTURE.md`.

При наличии существующих в проекте стандартов всегда следуй им в первую очередь:

- способу организации модулей;
- библиотеке UI-компонентов;
- инструментам состояния;
- маршрутизации;
- подходу к API-клиентам;
- настройкам ESLint, Prettier, TypeScript;
- тестовым утилитам;
- подходу к локализации.

Не добавляй новый state manager, UI-kit, CSS framework, form library или data-fetching library без обоснованной необходимости и явного согласования.

## Основные принципы

Пиши frontend-код, который:

- понятен и предсказуем;
- строго типизирован;
- доступен для пользователей с ограничениями;
- корректно обрабатывает loading, empty и error states;
- устойчив к медленным сетям и частичным ошибкам;
- не содержит дублирующейся бизнес-логики;
- не передаёт секреты в браузер;
- не создаёт лишних перерисовок и запросов;
- не смешивает представление, бизнес-правила и доступ к API.

Следуй принципам:

- **KISS** — выбирай самый простой поддерживаемый подход.
- **DRY** — выноси действительно повторяющуюся логику, но не создавай абстракцию для двух случайно похожих строк.
- **Single Responsibility** — компоненты, hooks и сервисы должны иметь узкую и понятную ответственность.
- **Composition over inheritance** — собирай интерфейс из небольших компонентов.
- **Progressive disclosure** — не перегружай интерфейс редкими настройками и действиями.
- **Server state is not client state** — серверные данные, состояние формы и локальное UI-состояние имеют разные жизненные циклы и не должны смешиваться без необходимости.

## TypeScript

Новый код должен быть написан на TypeScript, если проект не устанавливает иное правило.

### Обязательные правила

- Не используй `any`.
- Не используй небезопасные type assertions (`as SomeType`) для обхода ошибок типов.
- Предпочитай `unknown` для неизвестных данных с последующей проверкой.
- Включай строгую типизацию в соответствии с настройками проекта.
- Описывай публичные props, return type сложных hooks и контракты API.
- Для ограниченного набора значений используй union type или enum-подход, принятый в проекте.
- Отличай optional поле от поля, которое может быть `null`.
- Не дублируй типы API вручную, если в проекте есть генерация типов из OpenAPI.
- Не используй типы сущностей backend как UI-модели без необходимости: при сложной трансформации создавай отдельную view model.

### Предпочтительные примеры

```ts
type OrderStatus = "NEW" | "PAID" | "PROCESSING" | "COMPLETED";

interface OrderSummary {
  id: string;
  status: OrderStatus;
  createdAt: string;
  totalAmount: number;
}
```

```ts
function isApiError(value: unknown): value is { message: string; code: string } {
  return (
    typeof value === "object" &&
    value !== null &&
    "message" in value &&
    "code" in value
  );
}
```

## Структура кода

Предпочитай feature-based организацию:

```text
src/
├── app/                    # Инициализация приложения, providers, routing
├── pages/                  # Страницы маршрутов
├── features/               # Пользовательские сценарии и бизнес-функции
│   └── orders/
│       ├── api/
│       ├── components/
│       ├── hooks/
│       ├── model/
│       ├── utils/
│       └── tests/
├── entities/               # Переиспользуемые доменные UI-сущности
├── shared/
│   ├── api/
│   ├── components/
│   ├── hooks/
│   ├── lib/
│   ├── types/
│   └── ui/
└── assets/
```

Используй существующую структуру репозитория, если она уже принята.

### Правила зависимостей

- `shared` не зависит от `features` и `pages`.
- `entities` не зависит от конкретных страниц.
- `pages` собирают сценарии, но не содержат сложную бизнес-логику.
- `features` содержат логику конкретного пользовательского действия.
- API-клиенты не должны импортировать React-компоненты.
- UI-компоненты не должны выполнять прямые HTTP-запросы.
- Не создавай циклических импортов.
- Не импортируй внутренние файлы другого модуля, если модуль предоставляет публичный API.

## React-компоненты

### Компоненты должны быть небольшими

Разделяй компонент, если он одновременно:

- загружает данные;
- содержит сложную бизнес-логику;
- управляет формой;
- форматирует данные;
- отображает большую часть страницы;
- содержит несколько самостоятельных UI-блоков.

Разделение должно делать код понятнее, а не создавать множество файлов без пользы.

### Props

- Props должны быть минимальными и семантически понятными.
- Не передавай большие объекты, если компоненту нужны 1–2 поля.
- Не передавай флаги, меняющие компонент на несвязанные варианты поведения; лучше создай отдельные композиции или компоненты.
- Используй callbacks с понятными именами: `onSubmit`, `onCancel`, `onOrderSelect`.
- Не изменяй props.
- Не храни в state данные, которые полностью выводятся из props.

### Hooks

- Вызывай hooks только на верхнем уровне React-компонента или пользовательского hook.
- Пользовательский hook должен инкапсулировать переиспользуемую логику, а не быть формальной обёрткой.
- Не используй `useEffect` для вычисления значения, которое можно получить непосредственно во время render.
- Не используй `useEffect` как замену обработчика пользовательского действия.
- Следи за полным и корректным списком зависимостей в `useEffect`.
- Не отключай правила линтера для hooks без обоснованной причины.
- Используй `useMemo` и `useCallback` только после измерения проблемы либо при необходимости стабильной ссылки для корректности.

## Работа с серверными данными

Серверное состояние должно быть отделено от локального UI-state.

Для запросов:

- используй централизованный API-клиент проекта;
- передавай cancellation signal, если библиотека и проект это поддерживают;
- обрабатывай loading, success, empty, error и retry states;
- не выполняй один и тот же запрос из нескольких компонентов без необходимости;
- корректно обновляй или инвалидируй кэш после мутаций;
- не сохраняй серверные ответы в глобальном UI-state без причины;
- не считай ответ API доверенным: учитывай неполные, устаревшие или ошибочные данные.

Для операций изменения данных:

- блокируй повторную отправку формы, пока запрос выполняется;
- показывай понятный результат действия;
- обрабатывай конфликты, ошибки валидации и ошибки сети;
- применяй optimistic update только там, где есть понятная стратегия отката;
- не показывай пользователю «успех» до подтверждения успешного результата сервером.

## Формы и валидация

- Валидация на frontend улучшает UX, но не заменяет серверную валидацию.
- Для каждой формы реализуй состояния `idle`, `submitting`, `success` и `error`, если они применимы.
- Сообщения об ошибках должны быть конкретными и располагаться рядом с полем или в понятном summary-блоке.
- Сохраняй введённые пользователем значения после серверной ошибки, если это безопасно.
- Не очищай форму до успешного подтверждения операции.
- Используй семантически корректные типы полей: `email`, `password`, `number`, `date`, `tel` и другие.
- Не выводи технические детали backend-ошибок напрямую пользователю.

## Доступность

Каждый новый или изменённый интерфейс должен быть доступным.

Минимальные требования:

- используй семантические HTML-элементы;
- кнопка должна быть `<button>`, ссылка — `<a>`;
- все интерактивные элементы должны быть доступны с клавиатуры;
- у input должен быть связанный label;
- не передавай смысл исключительно цветом;
- добавляй текстовые описания и ARIA-атрибуты только когда нативной семантики HTML недостаточно;
- обеспечивай видимый focus state;
- корректно управляй фокусом в modal, dialog и после критичных действий;
- сообщения об ошибках и успешных действиях должны быть доступны screen reader;
- изображения должны иметь осмысленный `alt`, если они несут информацию;
- проверяй контраст текста и интерактивных элементов.

Не используй `div` с `onClick` вместо нативной кнопки.

## Стилизация и дизайн-система

- Используй компоненты, токены, темы и правила дизайн-системы проекта.
- Не создавай локальные «почти такие же» кнопки, поля и модальные окна, если уже есть стандартный компонент.
- Не используй inline styles, если в проекте принят иной способ стилизации.
- Не добавляй глобальные CSS-правила без необходимости.
- Не используй `!important`, кроме редких и обоснованных случаев.
- Поддерживай адаптивность на целевых разрешениях проекта.
- Проверяй состояние интерфейса при длинных строках, пустых данных, ошибках и медленной загрузке.
- Не хардкодь отображаемые тексты, даты, валюты и форматы, если проект поддерживает i18n.

## Обработка ошибок

Разделяй ошибки:

- ошибка валидации ввода;
- ошибка авторизации;
- недостаточно прав;
- отсутствие сущности;
- конфликт состояния;
- ошибка сети;
- временная недоступность сервиса;
- непредвиденная ошибка.

Пользователь должен получить понятное и безопасное сообщение. Технический контекст отправляй в систему мониторинга в соответствии с правилами проекта, не раскрывая чувствительные данные.

## Производительность

Не оптимизируй преждевременно. Сначала определи источник проблемы.

При работе со списками и большими объёмами данных:

- используй стабильный уникальный `key`, а не индекс массива;
- применяй пагинацию, infinite scroll или виртуализацию только по реальной необходимости;
- не рендери скрытые тяжёлые компоненты без необходимости;
- не загружай крупные данные до того, как они понадобятся;
- используй code splitting для тяжёлых, редких или маршрутизируемых разделов, если это соответствует архитектуре проекта;
- избегай ненужных повторных запросов и ререндеров.

## Тестирование

Добавляй тесты пропорционально риску изменения.

Минимальные требования:

- тестируй пользовательское поведение, а не внутреннюю реализацию компонента;
- для сложной бизнес-логики добавляй unit-тесты;
- для критичных пользовательских сценариев добавляй component/integration тесты;
- для ключевых сквозных сценариев добавляй E2E-тесты, если инфраструктура проекта это поддерживает;
- моки должны отражать реальный контракт API;
- не тестируй детали реализации, CSS-классы или приватные функции без необходимости;
- не отключай существующие тесты ради зелёной сборки.

## Перед завершением задачи

Перед завершением:

1. Убедись, что TypeScript-проверка проходит.
2. Запусти lint и форматирование в соответствии с командами проекта.
3. Выполни релевантные тесты.
4. Проверь UI для loading, empty, error и success states.
5. Проверь доступность изменённых интерактивных элементов.
6. Укажи в отчёте изменённые файлы, тесты, ограничения и не выполненные проверки.
