# Security guidelines

## Цель

Безопасность — обязательная часть проектирования, реализации, тестирования и ревью.

Все решения должны соблюдать принципы:

- least privilege;
- secure by default;
- defence in depth;
- zero trust для внешнего ввода и интеграций;
- минимизация собираемых и хранимых данных;
- явная проверка прав доступа;
- безопасная обработка ошибок;
- аудит критичных действий;
- своевременное обновление зависимостей.

Если выполнение задачи требует ослабления защиты, доступа к секретам, изменения прав, отключения проверок или хранения чувствительных данных — остановись, опиши риск и запроси явное подтверждение.

## Защита секретов

Никогда не добавляй в репозиторий, исходный код, тестовые фикстуры, логи или документацию:

- пароли;
- API keys;
- access tokens;
- refresh tokens;
- private keys;
- сертификаты;
- connection strings с учётными данными;
- секреты OAuth/OIDC;
- данные production-пользователей;
- платёжные реквизиты;
- реальные персональные данные.

Правила:

- Получай секреты только из approved secret manager, переменных окружения или механизмов конфигурации, принятых в проекте.
- Не хардкодь значения секретов даже для «временной проверки».
- Используй `.env.example` только с фиктивными значениями и без действительных идентификаторов.
- Не выводи секреты в логи, исключения, метрики, трассировки или сообщения об ошибках.
- Не включай секреты в URL и query parameters.
- Не коммить файлы `.env`, keystore, private key, локальные credentials и дампы БД.
- При обнаружении секрета в репозитории не копируй его и не публикуй в ответе; укажи файл, риск и необходимость отзыва/ротации.

## Аутентификация

Используй существующий корпоративный или проектный механизм аутентификации. Не реализуй собственную криптографию, генерацию токенов или password storage без отдельной необходимости и экспертного ревью.

Правила:

- Проверяй подпись, issuer, audience, срок действия и другие обязательные claims токенов в соответствии с используемым протоколом.
- Не доверяй данным пользователя, переданным клиентом, если они доступны из authentication context.
- Не реализуй «временный обход авторизации» для локального удобства без строго ограниченной non-production конфигурации.
- Не передавай access token через query parameters.
- Не сохраняй долгоживущие секреты в `localStorage`, если архитектура допускает безопасную альтернативу.
- При использовании cookie применяй безопасные флаги: `HttpOnly`, `Secure`, подходящий `SameSite`.
- Ограничивай время жизни сессий и токенов в соответствии с требованиями проекта.
- Обрабатывай logout и отзыв сессии в соответствии с принятой моделью аутентификации.
- Не сообщай пользователю, существует ли конкретная учётная запись, если это создаёт риск enumeration.

## Авторизация

Авторизация должна проверяться на сервере для каждого защищённого действия.

Обязательные правила:

- Проверяй не только роль, но и право доступа к конкретному ресурсу.
- Не полагайся на скрытые кнопки и ограничения frontend как на механизм защиты.
- Не принимай `userId`, `tenantId`, `organizationId`, `role` или `permissions` из клиентского запроса как источник истины.
- Извлекай субъект, tenant и полномочия из доверенного authentication context.
- Применяй принцип минимально необходимых прав.
- Явно определяй доступ для чтения, создания, обновления, удаления и административных операций.
- Проверяй ownership и tenant isolation при доступе к данным.
- Не разрешай массовые операции без явной проверки прав и ограничений области действия.
- Логируй и аудируй критичные административные действия, изменения прав и доступ к чувствительным данным.

Пример небезопасного подхода:

```json
{
  "userId": "another-user-id",
  "role": "ADMIN"
}
```

Не используй данные из тела запроса для определения полномочий пользователя.

## Валидация входных данных

Считай недоверенными все данные, поступающие извне:

- HTTP request body;
- path variables;
- query parameters;
- headers;
- cookie;
- файлы;
- сообщения из очередей;
- webhook payload;
- данные внешних API;
- конфигурацию, если её источник не контролируется.

Правила:

- Валидируй тип, формат, длину, диапазон и допустимые значения.
- Используй allowlist вместо denylist, где это возможно.
- Ограничивай размер JSON payload, файлов, массивов и строк.
- Ограничивай глубину вложенных структур.
- Не десериализуй произвольные классы по данным клиента.
- Не используй небезопасную динамическую интерпретацию данных: `eval`, выполнение shell-команд, небезопасная reflection-логика.
- Валидируй URL перед исходящими запросами, если URL может быть задан пользователем.
- Не доверяй MIME type, имени файла и расширению при загрузке файлов.

## Защита от распространённых уязвимостей

### SQL injection

- Используй параметризованные запросы, prepared statements, JPA criteria или безопасные query builder.
- Никогда не собирай SQL конкатенацией пользовательских строк.
- Не подставляй пользовательские значения в `ORDER BY`, имя таблицы, колонки или части SQL без строгого allowlist.
- Используй отдельную учётную запись БД с минимальными правами.

### XSS

- Не вставляй пользовательский или внешний HTML через `dangerouslySetInnerHTML` без строгой необходимости и надёжной санитизации.
- По умолчанию React экранирует текст — не обходи этот механизм.
- Не используй `eval`, `new Function` и небезопасные динамические скрипты.
- При отображении rich text применяй проверенную санитизацию согласно правилам проекта.
- Устанавливай Content Security Policy, если это поддерживается инфраструктурой.
- Не передавай чувствительные данные в HTML, JavaScript bundle или browser storage.

### CSRF

Если аутентификация основана на cookie:

- применяй CSRF-защиту;
- проверяй origin/referer в соответствии с политикой проекта;
- используй `SameSite` cookie;
- не отключай CSRF-защиту глобально без обоснования и альтернативных контролей.

### SSRF

Для функций, принимающих URL:

- разрешай только необходимые схемы, обычно `https`;
- используй allowlist доменов, если это возможно;
- блокируй обращения к localhost, private network, metadata endpoints и внутренним адресам;
- ограничивай redirects;
- устанавливай timeout и лимит ответа;
- не возвращай клиенту содержимое внутренних ответов.

### Path traversal и файловые операции

- Не используй клиентское имя файла как путь на диске.
- Генерируй серверное имя файла.
- Нормализуй путь и проверяй, что он находится внутри разрешённой директории.
- Не разрешай загрузку исполняемых файлов, если это не является явной функцией системы.
- Проверяй размер, тип, содержимое и при необходимости сканируй файл антивирусом.
- Храни загруженные файлы вне web root или в специализированном object storage.
- Не доверяй расширению файла.

### Command injection

- Не передавай пользовательские данные в shell-команды.
- Избегай запуска shell из приложения.
- Если запуск процесса необходим, используй аргументированный API без shell-интерпретации.
- Используй allowlist допустимых команд и аргументов.
- Запускай процессы с минимальными правами и строгими timeout.

### Insecure deserialization

- Не десериализуй недоверенные Java serialized objects.
- Не разрешай polymorphic deserialization для недоверенного JSON без строгого allowlist типов.
- Используй безопасные форматы обмена и явные DTO.
- Валидируй входные структуры после десериализации.

## Пароли и криптография

- Не разрабатывай собственные криптографические алгоритмы.
- Не используй MD5, SHA-1, обратимое шифрование или быстрые хеши для хранения паролей.
- Для паролей используй современные password hashing algorithms, одобренные стеком проекта, например Argon2id, bcrypt или PBKDF2 с корректными параметрами.
- Для случайных токенов и идентификаторов безопасности используй криптографически стойкий генератор случайных чисел.
- Используй проверенные библиотеки и встроенные механизмы платформы.
- Не храни encryption key рядом с зашифрованными данными.
- Не логируй исходные пароли, коды восстановления, одноразовые коды и токены.
- Не сравнивай чувствительные токены небезопасным способом, если библиотека предоставляет constant-time comparison.

## Персональные и чувствительные данные

Собирай и храни только данные, необходимые для продукта.

Правила:

- Минимизируй состав персональных данных в API, логах, аналитике и тестах.
- Маскируй чувствительные значения в логах и интерфейсах.
- Ограничивай доступ к данным по ролям, ownership и tenant.
- Не используй production-данные в локальной разработке и тестах без утверждённого процесса обезличивания.
- Определяй срок хранения данных, когда это требуется продуктом или регулированием.
- Не добавляй новые поля с персональными данными без оценки необходимости, доступа и жизненного цикла.
- Не передавай персональные данные внешним сервисам без явной необходимости и согласованного контракта.

## Безопасность API

- Все endpoint-ы должны иметь явно определённую политику: публичный, аутентифицированный или требующий специальных прав.
- Защищай endpoint-ы от brute force и злоупотреблений с помощью rate limiting, captcha или иных механизмов там, где это оправдано.
- Устанавливай ограничения на request body, upload и pagination size.
- Используй TLS для всех внешних соединений в production.
- Не включай debug endpoints, Swagger UI, actuator endpoints и тестовые административные функции в production без соответствующей защиты.
- Ограничивай CORS конкретными доверенными origins, методами и заголовками.
- Не используй wildcard CORS вместе с credentials.
- Устанавливай разумные timeout для исходящих HTTP-вызовов.
- Проверяй подпись, timestamp и защиту от replay для webhook, если это поддерживает провайдер.

## Зависимости и supply chain

- Не добавляй зависимости без необходимости.
- Предпочитай поддерживаемые, распространённые и совместимые с проектом библиотеки.
- Проверяй репутацию, лицензию, актуальность и известные уязвимости новой зависимости.
- Не подключай библиотеку ради одной простой утилитарной функции, которую безопасно предоставляет стандартная библиотека.
- Не обновляй зависимости массово в рамках несвязанной продуктовой задачи.
- При устранении уязвимости фиксируй версию зависимости и добавляй тесты, если риск затрагивает поведение приложения.
- Не отключай dependency scanning, secret scanning, SAST или другие проверки безопасности для прохождения CI.

## Логирование, аудит и обработка ошибок

- Логи должны помогать расследованию, но не раскрывать чувствительные данные.
- Добавляй correlation ID / trace ID, если это принято в проекте.
- Разделяй пользовательские сообщения об ошибках и технические детали.
- Не возвращай stack trace, SQL, конфигурацию или внутренние адреса клиенту.
- Аудируй события, связанные с правами, доступом к чувствительным данным, изменением настроек безопасности и критичными бизнес-операциями.
- Аудит должен содержать кто, что, когда и над каким ресурсом сделал, но не должен содержать секреты.
- Не записывай успешные authentication credentials, токены или полные request body в логи.

## Security checklist перед завершением

Перед завершением задачи проверь:

1. Не добавлены ли секреты, реальные ключи, токены или персональные данные.
2. Валидируются ли все новые входные параметры.
3. Есть ли серверная проверка аутентификации и авторизации.
4. Проверяется ли ownership/tenant isolation для доступа к ресурсу.
5. Нет ли SQL, XSS, SSRF, path traversal, command injection или небезопасной десериализации.
6. Не передаются ли чувствительные данные в URL, логи, ошибки или frontend bundle.
7. Ограничены ли размеры входных данных, файлов, пагинации и дорогих операций.
8. Установлены ли timeout и безопасная обработка ошибок для новых интеграций.
9. Не нарушена ли обратная совместимость политик доступа и API.
10. Добавлены ли или обновлены security-, unit- и integration-тесты пропорционально риску.

Если хотя бы один пункт требует компромисса, явно укажи его в итоговом отчёте: риск, причина, затронутые компоненты и рекомендуемое дальнейшее действие.
