# Java style

## Базовые принципы

- Обязательно соблюдай [Code Conventions for the Java Programming Language](https://www.oracle.com/a/tech/docs/java/codeconventions.pdf). При конфликте с локальными правилами проекта приоритет имеют локальные правила.
- Используй Java 21 и возможности языка, уже принятые в проекте.
- Следуй существующей архитектуре, соглашениям именования, структуре пакетов и стилю модуля.
- Не выполняй массовое форматирование, переименование или рефакторинг несвязанных файлов.
- Предпочитай простой, очевидный и сопровождаемый код сложным абстракциям.
- Применяй SOLID, DRY и KISS прагматично: не создавай лишние уровни абстракции ради формального следования паттерну.
- Каждая сущность, класс и метод должны иметь одну ясную ответственность.
- Предпочитай композицию наследованию; наследование используй только при реальном отношении «является» и устойчивой иерархии.
- Не добавляй design pattern без конкретной решаемой проблемы. Паттерн должен упрощать развитие кода, а не усложнять чтение.
- Не используй преждевременную оптимизацию. Оптимизации должны быть обоснованы профилированием, метриками или известными требованиями нагрузки.

## Структура и именование

- Имена должны раскрывать бизнес-смысл и намерение, а не техническую реализацию.
- Не используй неинформативные имена: `data`, `value`, `item`, `tmp`, `result`, `handler`, если контекст не делает их смысл однозначным.
- Используй существительные для классов и объектов, глаголы для методов, булевы префиксы `is`, `has`, `can`, `should` для логических значений.
- Не добавляй суффиксы `Impl`, `Manager`, `Helper`, `Util`, `Common` без необходимости и понятной роли.
- Один публичный класс верхнего уровня — один файл; имя файла соответствует имени класса.
- Пакеты называй в нижнем регистре, без символов подчёркивания.
- Не создавай «god class» или «god service». Если класс объединяет несколько бизнес-ответственностей, раздели его по связности.
- Не смешивай HTTP-слой, бизнес-логику, доступ к данным и интеграционную логику в одном классе.

## Классы, методы и зависимости

- Делай классы и методы настолько маленькими, насколько это сохраняет целостность и читаемость.
- Метод должен выполнять одну законченную операцию и иметь понятный контракт.
- Избегай длинных методов с вложенной логикой. Используй guard clauses и извлекай самостоятельные части в методы.
- Старайся ограничивать число параметров метода. Если параметров много и они образуют логическую группу, введи объект параметров или команду.
- Не передавай `Map<String, Object>` вместо явных типов, DTO или value objects, кроме действительно динамических интеграционных сценариев.
- Используй dependency injection через конструктор. Не применяй field injection.
- Зависимости класса должны быть минимальными и явно выраженными.
- Не создавай сервис-локаторы, глобальное изменяемое состояние и скрытые зависимости.
- Избегай статических mutable-полей. Они особенно опасны для многопоточных приложений и тестов.
- Не возвращай `null` из публичных методов без явно принятого контракта. Используй `Optional` для отсутствующего результата, когда это уместно.
- Не используй `Optional` в полях JPA-сущностей, параметрах методов, DTO и коллекциях.
- Публичные API не должны возвращать внутренние изменяемые коллекции. Возвращай неизменяемые представления или копии.
- Предпочитай интерфейсы в типах полей, аргументов и возвращаемых значений, если конкретная реализация не является частью контракта.

## Неизменяемость и данные

- Предпочитай неизменяемые объекты, особенно для DTO, команд, событий, конфигурации и value objects.
- Используй `record` для простых неизменяемых DTO и value objects, если это совместимо с фреймворками и стилем проекта.
- Не передавай JPA-сущности между слоями как внешний контракт. Преобразуй их в DTO или доменные модели.
- Не изменяй входные коллекции, DTO и объекты команд без явного и документированного контракта.
- Используй `BigDecimal` для денежных значений и финансовых расчётов. Не используй `double` или `float` для денег.
- Для времени используй `Instant`, `OffsetDateTime`, `LocalDate` и `Duration` согласно бизнес-смыслу.
- Не используй системное время напрямую в бизнес-логике, если требуется детерминированное тестирование; внедряй `Clock`.
- Явно указывай `ZoneId` при преобразовании между моментом времени и локальной датой/временем.
- Не используй строковые литералы для статусов, ролей, типов и кодов, если допустим enum, константа или типизированный объект.

## Потоки, null и обработка ошибок

- Используй Stream API для преобразований и декларативных операций над коллекциями, когда это повышает читаемость.
- Не используй Stream API для сложных побочных эффектов, отладки, изменения внешнего состояния или логики с запутанным ветвлением.
- Не вызывай `.get()` у `Optional` без предварительной проверки. Предпочитай `orElseThrow`, `map`, `flatMap`, `ifPresent`.
- Не перехватывай `Exception`, `Throwable` или широкие исключения без обоснованной причины.
- Не игнорируй исключения и не используй пустые блоки `catch`.
- Не используй исключения для нормального управления бизнес-потоком.
- Разделяй технические, инфраструктурные и бизнес-ошибки.
- Исключения должны содержать полезный контекст для диагностики, но не включать пароли, токены, ключи, персональные данные и полные HTTP-body.
- Сохраняй исходное исключение как `cause`, если ошибка оборачивается в более предметное исключение.
- Не раскрывай внутренние детали исключений через HTTP API. Преобразование ошибок выполняется на уровне централизованного обработчика.

## Spring и транзакции

- Контроллеры отвечают за HTTP-контракт: валидацию входных DTO, преобразование запроса и формирование ответа. Не размещай в них бизнес-логику.
- Бизнес-логику размещай в сервисах или доменных компонентах.
- Репозитории отвечают только за доступ к данным и не должны содержать бизнес-правила.
- Не передавай HTTP DTO непосредственно в repository-слой.
- Используй `@Transactional` на границах сервисных операций, а не на контроллерах.
- Для операций только чтения используй `@Transactional(readOnly = true)`, если это соответствует инфраструктуре проекта.
- Не вызывай транзакционный метод через `this`, если ожидается применение Spring proxy.
- Не выполняй долгие сетевые вызовы, файловые операции или внешние HTTP-запросы внутри открытой транзакции без явной необходимости.
- Избегай N+1-запросов, неявной lazy-загрузки в HTTP-слое и утечки persistence context за границы бизнес-операции.
- Не полагайся на порядок выполнения компонентов Spring, если он не закреплён явной конфигурацией.

## Конкурентность и производительность

- Считай серверный код многопоточным по умолчанию.
- Не храни состояние конкретного запроса в singleton bean, статических полях или разделяемых mutable-объектах.
- Для идемпотентных операций используй явные ключи идемпотентности, уникальные ограничения или другие надёжные механизмы защиты от повторного выполнения.
- Не используй `parallelStream()` без измеренного обоснования и понимания влияния на общие пулы потоков.
- Все внешние вызовы должны иметь timeout, контролируемую обработку ошибок и ограничение повторных попыток.
- Retry применяй только к безопасным, идемпотентным или защищённым идемпотентностью операциям.
- Не логируй большие объекты, полные payload, бинарные данные и коллекции неограниченного размера.
- Не загружай потенциально большие наборы данных целиком, если возможны пагинация, потоковая обработка или батчи.

## Логирование и наблюдаемость

- Логируй значимые бизнес- и технические события на подходящем уровне: `ERROR`, `WARN`, `INFO`, `DEBUG`, `TRACE`.
- Не используй `ERROR` для ожидаемых сценариев валидации или штатного отсутствия данных.
- Используй параметризованное логирование: `log.info("Order {} created", orderId)`.
- Не конкатенируй строки для логирования и не вычисляй дорогие значения, если соответствующий уровень лога отключён.
- В логах должны присутствовать безопасные идентификаторы для диагностики: request ID, correlation ID, entity ID, tenant ID — если они доступны и не являются секретом.
- Никогда не логируй пароли, access token, refresh token, cookie, ключи, платёжные реквизиты, персональные данные без маскирования.
- Для новых критичных операций добавляй или обновляй метрики, трассировку и структурированные логи в соответствии со стандартом проекта.

## Импорты, комментарии и документация

- Не используй wildcard-импорты.
- Удаляй неиспользуемые импорты, мёртвый код и закомментированные фрагменты, если они не требуются для совместимости.
- Комментарий должен объяснять причину, ограничение, инвариант или нетривиальное решение, а не пересказывать код.
- Добавляй JavaDoc для публичных библиотечных API, сложной бизнес-логики, неочевидных инвариантов и ограничений интеграций.
- В JavaDoc фиксируй контракт, предусловия, постусловия, побочные эффекты и исключения, если они важны для использования API.
- Не добавляй JavaDoc ради формальности к очевидным getter/setter и простым методам.

## Качество перед завершением

Перед завершением изменения:

1. Проверь корректность форматирования и статического анализа, принятых в проекте.
2. Убедись, что нет неиспользуемого кода, импортов и зависимостей.
3. Проверь обработку `null`, ошибок, границ коллекций и пустых результатов.
4. Проверь корректность транзакционных границ и отсутствие N+1-запросов в изменённом пути.
5. Проверь отсутствие секретов и чувствительных данных в коде, исключениях и логах.
6. Добавь или обнови тесты пропорционально риску изменения.
