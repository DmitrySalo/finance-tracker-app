# Architecture guidelines

## Цель

Проектируй и развивай систему так, чтобы она оставалась:

- понятной для сопровождения;
- безопасной;
- тестируемой;
- масштабируемой по мере реальной потребности;
- наблюдаемой в production;
- устойчивой к частичным отказам внешних систем;
- совместимой с существующими контрактами и данными.

Не усложняй решение заранее. Предпочитай простую архитектуру, которая покрывает текущие требования и имеет понятный путь эволюции.

## Приоритеты при принятии решений

При конфликте требований используй следующий порядок приоритета:

1. Корректность и целостность данных.
2. Безопасность.
3. Обратная совместимость публичных контрактов.
4. Надёжность и отказоустойчивость.
5. Понятность и сопровождаемость.
6. Производительность.
7. Скорость реализации.
8. Минимизация преждевременной сложности.

Всегда учитывай существующие правила, структуру и технологические ограничения проекта. Не внедряй новую архитектурную парадигму без явной необходимости.

## Базовые архитектурные принципы

Следуй следующим принципам:

- **Separation of Concerns** — каждый слой и компонент имеет чёткую область ответственности.
- **Single Responsibility Principle** — класс, модуль или сервис должен иметь одну основную причину для изменения.
- **Dependency Inversion** — бизнес-логика не должна зависеть от технических деталей, таких как HTTP, SQL, JPA, Kafka или конкретный внешний SDK.
- **Explicit over implicit** — важные зависимости, преобразования, транзакции, политики повторных попыток и права доступа должны быть явными.
- **Composition over inheritance** — предпочитай композицию наследованию, если наследование не отражает устойчивую доменную иерархию.
- **Convention over configuration** — используй сложившиеся соглашения проекта, но не скрывай критичное поведение за неочевидной магией.
- **Fail fast** — некорректную конфигурацию, нарушенные инварианты и неверные входные данные выявляй как можно раньше.
- **Defence in depth** — безопасность, валидация и контроль доступа должны выполняться на нескольких уровнях.
- **Design for change** — изолируй части системы, которые с высокой вероятностью будут меняться: внешние интеграции, правила тарификации, платёжные провайдеры, способы доставки, механизмы авторизации.

Не применяй паттерны только ради паттернов. Каждый дополнительный слой, интерфейс или абстракция должен решать конкретную проблему.

## Предпочтительная структура backend-модуля

Для Java/Spring Boot приложений придерживайся разделения на слои:

```text
src/main/java/com/example/project/
├── api/                  # HTTP-контроллеры, request/response DTO, обработчики ошибок
├── application/          # Use cases, orchestration, транзакционные сценарии
├── domain/               # Доменные сущности, value objects, бизнес-правила, domain events
├── infrastructure/       # JPA, SQL, очереди, внешние HTTP-клиенты, файловые хранилища
├── configuration/        # Spring-конфигурация, свойства, bean-конфигурация
└── shared/               # Небольшие общие технические компоненты
```

Допустимо использовать текущую структуру проекта, если она уже принята командой. Не выполняй массовую перестройку пакетов в рамках несвязанной задачи.

### Правила слоёв

- `api` не содержит бизнес-правила, SQL, JPA-запросы и логику интеграций.
- `api` преобразует HTTP DTO в команды или входные модели application-слоя.
- `application` координирует use case, транзакции, вызовы портов и доменной логики.
- `domain` не зависит от Spring, HTTP, JPA, Kafka, базы данных и внешних SDK.
- `infrastructure` реализует технические детали и интерфейсы, определённые ближе к application/domain слою.
- DTO API не должны использоваться как доменные объекты.
- JPA entity не должна становиться публичным API-контрактом.
- Контроллер не должен напрямую обращаться к `Repository`, кроме простых и явно согласованных случаев.

## Границы модулей и сервисов

Перед созданием нового модуля, микросервиса или отдельной базы данных оцени:

- независимость жизненного цикла и релизов;
- необходимость независимого масштабирования;
- границы владения данными;
- частоту и характер межмодульных взаимодействий;
- требования к доступности;
- операционную стоимость;
- сложность распределённых транзакций и согласованности.

По умолчанию предпочитай модульный монолит, если нет подтверждённой причины для выделения отдельного сервиса.

Не выделяй микросервис только потому, что доменных сущностей много или кодовая база выросла. Микросервис оправдан, когда есть ясная граница ответственности, отдельное владение данными и независимая потребность в поставке или масштабировании.

## Взаимодействие между компонентами

### Синхронное взаимодействие

Для синхронных запросов:

- явно определяй timeout;
- обрабатывай сетевые ошибки и недоступность зависимостей;
- не выполняй неограниченные повторные попытки;
- не передавай внутренние технические ошибки наружу;
- ограничивай объём возвращаемых данных;
- используй correlation ID для трассировки.

### Асинхронное взаимодействие

Для очередей, событий и асинхронной обработки:

- проектируй обработчики идемпотентными;
- учитывай повторную доставку сообщений;
- не полагайся на порядок доставки, если брокер и контракт его явно не гарантируют;
- версионируй формат сообщений;
- обрабатывай ошибки через retry policy и dead-letter queue, если это предусмотрено инфраструктурой;
- не публикуй событие до успешного завершения критичной транзакции;
- для согласованной публикации событий после записи в БД предпочитай паттерн transactional outbox.

Событие должно сообщать о факте, который уже произошёл, а не быть скрытой командой другому сервису.

## Данные и транзакции

- Один сервис или модуль должен иметь чёткое владение своими данными.
- Не предоставляй другим сервисам прямой доступ к внутренней базе данных.
- Не используйте распределённые транзакции без крайней необходимости.
- При работе между сервисами предпочитай eventual consistency с явной обработкой промежуточных состояний.
- Чётко определяй границу транзакции в application-слое.
- Не выполняй долгие сетевые вызовы внутри открытой транзакции БД.
- Для операций изменения данных определяй инварианты, конкурентное поведение и стратегию обработки конфликтов.
- Для защиты от lost update используй оптимистическую блокировку или другую подходящую стратегию.
- Изменения схемы выполняй только через миграции, принятые в проекте.

## Производительность и масштабирование

Перед оптимизацией сначала измерь проблему: используй профилирование, метрики, логи запросов, трассировки или данные мониторинга.

Обязательные практики:

- не загружай неограниченные коллекции из БД;
- используй пагинацию для списочных API;
- предотвращай N+1 запросы;
- выбирай только необходимые поля, если полная сущность не нужна;
- добавляй индексы для реально используемых путей поиска и сортировки;
- не кэшируй данные без ясной политики инвалидации;
- не создавай кэш ради производительности без измеренной необходимости;
- устанавливай ограничение размера запросов, ответов и batch-операций;
- оценивай влияние изменений на latency, throughput, память и нагрузку на БД.

## Наблюдаемость

Все production-компоненты должны быть наблюдаемыми.

При реализации затрагивай наблюдаемость, если это необходимо:

- структурированные логи;
- уровень логирования, соответствующий серьёзности события;
- correlation ID / trace ID;
- метрики ошибок, latency, количества запросов и фоновых задач;
- health checks для критичных зависимостей;
- понятные сообщения об ошибках без утечки чувствительных данных;
- аудит бизнес-критичных действий, если это необходимо.

Не записывай в логи пароли, токены, cookie, секреты, полные платёжные данные, персональные данные и содержимое авторизационных заголовков.

## Обратная совместимость

Не изменяй существующее поведение без явной необходимости.

Для публичных API, событий, миграций и интеграций:

- не удаляй поля без периода deprecation;
- не меняй значение или семантику существующего поля;
- не меняй тип поля без стратегии миграции;
- новые поля делай опциональными, если контракт не был версионирован;
- не меняй формат ошибки без согласования;
- не изменяй порядок бизнес-процесса, если он доступен внешним потребителям;
- для несовместимых изменений используй новую версию API или отдельный контракт.

## Проверка архитектурного решения

До реализации нетривиального изменения кратко опиши:

1. Проблему и границы изменения.
2. Затрагиваемые модули и данные.
3. Варианты решения, если их больше одного.
4. Выбранный вариант и причины выбора.
5. Изменения API, схемы БД и интеграций.
6. Риски, ограничения и стратегию отката.
7. Необходимые тесты и проверки.

Не создавай отдельный архитектурный документ для небольшой локальной задачи, если текущий контекст и финальный отчёт полностью покрывают решение.
