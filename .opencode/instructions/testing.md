# Testing

## Цели и основные принципы

- Тесты должны подтверждать поведение системы и защищать от регрессий, а не только повышать покрытие.
- Для каждого исправленного дефекта добавь регрессионный тест, если это технически возможно.
- Для новой бизнес-логики добавляй unit-тесты.
- Каждый тест должен проверять один понятный сценарий или один бизнес-инвариант.
- Тесты должны быть независимыми, повторяемыми и не зависеть от порядка запуска.
- Тесты не должны зависеть от текущей даты, локальной временной зоны, сети, случайности, состояния машины или внешних систем.
- Не отключай, не удаляй и не ослабляй существующие тесты ради прохождения сборки.
- Не используй `Thread.sleep`, произвольные ожидания и гонки состояний. Используй детерминированные синхронизационные механизмы, виртуальное время или polling с ограниченным timeout, если это необходимо.
- Не тестируй детали реализации, если можно протестировать публичное поведение и бизнес-контракт.
- Не добавляй тесты, которые зависят от приватных методов, внутренней структуры класса или конкретного порядка служебных вызовов без существенной причины.

## Пирамида тестирования

- Предпочитай быстрые unit-тесты для бизнес-правил, преобразований, валидации, расчётов и обработки ошибок.
- Используй интеграционные тесты для проверки взаимодействия с Spring, базой данных, брокером сообщений, файловой системой, HTTP-клиентом или конфигурацией.
- Используй end-to-end тесты только для ключевых пользовательских потоков и критичных интеграций.
- Не заменяй unit-тестами необходимость проверить важную инфраструктурную интеграцию.
- Не используй тяжёлый Spring context, если сценарий можно достоверно проверить обычным unit-тестом.
- Для изменения API добавляй тесты HTTP-контракта и проверки кодов ответов, валидации, авторизации и структуры ошибок.
- Для изменений в БД добавляй интеграционные тесты миграций, запросов и ограничений данных, если это релевантно.

## Структура тестов

- Используй шаблон Arrange–Act–Assert.
- В одном тесте должен быть один основной `Act`.
- Секции теста отделяй пустыми строками или логическими блоками, если это повышает читаемость.
- Называй тесты так, чтобы было понятно условие, действие и ожидаемый результат.

Пример:
```java
@Test
void shouldRejectOrderCreationWhenProductIsInactive() {
    // Arrange
    var product = inactiveProduct();
    var command = createOrderCommand(product.id());

    // Act
    var exception = assertThrows(
        ProductUnavailableException.class,
        () -&gt; orderService.create(command)
    );

    // Assert
    assertThat(exception.getProductId()).isEqualTo(product.id());
}
```

- Не используй неинформативные имена: `test1`, `successTest`, `shouldWork`.
- Не скрывай важные входные данные в больших общих fixture без необходимости.
- Предпочитай локальные тестовые данные и фабрики с читаемыми значениями.
- Создавай test data builder или object mother для сложных объектов, но не допускай неявных значений, которые затрудняют понимание сценария.
- В тесте меняй только те данные, которые важны для конкретного сценария.

## Unit-тесты

- Unit-тесты не должны поднимать Spring context, подключаться к БД, сети, очередям или файловой системе.
- Тестируй бизнес-правила через публичные методы сервисов и доменных объектов.
- Моки должны заменять внешние границы системы: repository, HTTP-клиенты, брокеры, часы, файловую систему и интеграционные адаптеры.
- Не мокай простые value objects, DTO, коллекции и логику, которую можно создать реально.
- Не проверяй каждый внутренний вызов mock-объекта, если контракт результата уже проверен.
- Проверка взаимодействий допустима, когда взаимодействие является частью важного контракта: отправка события, вызов внешнего сервиса, запись в repository.
- Используй строгие проверки аргументов для критичных side effect: идентификаторов, статусов, сумм, tenant ID, idempotency key.
- Не используй широкие matcher-ы (`any()`, `anyString()`) там, где важна точность передаваемых данных.
- Для проверки исключений проверяй тип, ключевые поля и бизнес-код ошибки, а не только факт выброса исключения.
- Проверяй граничные случаи: пустые значения, максимальные размеры, некорректные статусы, дубликаты, конкурентные обновления и ошибки зависимостей.
- Каждый Java-тест должен иметь `@DisplayName` с кратким описанием проверяемого кейса на русском языке.

## Интеграционные тесты

- Поднимай только минимально необходимую инфраструктуру.
- Предпочитай тестовые контейнеры или эквивалентное окружение, максимально близкое к production-версии зависимостей.
- Не используй in-memory БД как единственную проверку SQL-совместимости, миграций, индексов и диалекта PostgreSQL.
- Интеграционные тесты не должны обращаться к реальным внешним сервисам, production-системам или общим тестовым окружениям без явной необходимости.
- Для внешних HTTP-интеграций используй mock server, stub или контрактный тест.
- Для асинхронных сценариев проверяй итоговое наблюдаемое состояние, событие или ответ, а не завязывайся на фиксированные задержки.
- При работе с базой данных очищай состояние между тестами предсказуемым способом и не допускай утечек данных между сценариями.
- Не полагайся на последовательность выполнения тестовых классов.
- Явно проверяй транзакционные границы, уникальные ограничения, foreign key, индексы и миграции там, где они являются частью изменения.
- PostgreSQL-контейнер для Java-интеграционных тестов должен быть единым на JVM; не создавай отдельный контейнер в каждом test-классе, если сценарий не требует изолированной конфигурации базы.
- Spring context должен переиспользоваться через общий базовый тест и одинаковую конфигурацию. Создавай отдельный context только при отличающихся bean-ах, свойствах, профиле или инфраструктурной конфигурации, необходимых сценарию.
- Перед каждым Java-интеграционным тестом очищай бизнес-таблицы PostgreSQL в транзакции. Очистка должна учитывать foreign key и триггеры, не удалять схему и не менять примененные миграции.
- Если тест проверяет результат стартовой или seed-миграции, выполняй его миграции в отдельной временной схеме того же контейнера и очищай эту схему после проверки; не позволяй его данным и истории Flyway влиять на другие сценарии.
- Каждый Java-тест должен иметь `@DisplayName` с кратким описанием проверяемого кейса на русском языке.

## Тестирование HTTP API

- Проверяй успешные ответы, ошибки валидации, отсутствие аутентификации, недостаточность прав и доступ к чужому ресурсу.
- Проверяй HTTP-статусы, обязательные поля ответа, типы данных, формат дат, пагинацию, сортировку и error contract.
- Не проверяй весь JSON строковым сравнением, если это делает тест хрупким; используй JSONPath, deserialization или специализированные assertion-библиотеки.
- Проверяй, что внутренние stack trace, SQL-детали, конфиденциальные данные и технические исключения не раскрываются в API.
- Для изменений публичного API поддерживай обратную совместимость или добавляй явно согласованный план миграции.
- Для критичных внешних контрактов используй contract testing или OpenAPI-based проверки, если это принято в проекте.

## Время, случайность и асинхронность

- Используй внедряемый `Clock` вместо обращения к системному времени в тестируемой бизнес-логике.
- Явно фиксируй временную зону в тестах, где время и дата важны.
- Используй фиксированный seed для случайных данных либо заменяй генератор детерминированным.
- Не допускай flaky-тестов. Если тест нестабилен, исправь причину, а не увеличивай timeout.
- Все timeout должны быть короткими, обоснованными и не использоваться вместо корректной синхронизации.
- Для реактивного или асинхронного кода используй инструменты тестирования соответствующего стека: virtual time, awaitility-подобные механизмы или явные completion signals.

## Данные, безопасность и приватность

- Не используй в тестах реальные персональные данные, production-выгрузки, реальные токены, пароли, ключи или секреты.
- Тестовые данные должны быть синтетическими и безопасными для логов и CI.
- Добавляй негативные тесты для валидации, авторизации, tenant isolation, ownership и попыток обхода ограничений.
- Для уязвимых областей добавляй тесты на некорректные входные данные, SQL injection, XSS, path traversal, SSRF и неправильную десериализацию — если применимо к изменению.
- Проверяй, что чувствительные значения не попадают в сообщения об ошибках и логи.

## Покрытие и качество

- Покрытие кода — индикатор, а не цель. Не повышай его искусственными тестами без проверяемого поведения.
- Критичные бизнес-правила, расчёты, разрешения доступа, платежи, миграции и обработка ошибок должны иметь высокий уровень проверок.
- Добавляй тест на каждую важную ветку поведения, включая отрицательные и граничные сценарии.
- При изменении дефекта сначала стремись воспроизвести его тестом, затем исправляй реализацию.
- Не принимай тест, который проходит независимо от правильности реализации.
- Проверяй, что assertions способны обнаружить предполагаемую регрессию.

## Выполнение перед завершением

Перед завершением задачи:

1. Выполни минимум тесты затронутого модуля.
2. Выполни статический анализ, линтеры и проверку форматирования, принятые в проекте.
3. Для изменений схемы данных выполни тесты миграций и интеграционные тесты repository-слоя.
4. Для изменения публичного API выполни тесты HTTP-контракта, валидации и авторизации.
5. Для исправления дефекта убедись, что новый тест падает на прежнем поведении и проходит после исправления, если это возможно.
6. В итоговом отчёте укажи выполненные команды, их результат и невыполненные проверки с причиной.
