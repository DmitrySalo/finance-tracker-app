# API contracts guidelines

## Цель

Публичный HTTP API — это долгосрочный контракт между frontend, backend, мобильными клиентами, интеграциями и внешними потребителями.

При проектировании API приоритетны:

1. Предсказуемость.
2. Обратная совместимость.
3. Безопасность.
4. Ясная семантика.
5. Единообразие.
6. Наблюдаемость.
7. Производительность.

Не изменяй существующий контракт без явной необходимости и понятной стратегии миграции.

## Общие правила

- API должен быть ресурсно-ориентированным, если это не ухудшает ясность доменной модели.
- Используй JSON и UTF-8, если проектом не определён другой формат.
- Используй существующий базовый путь и версионирование API.
- Новые endpoint-ы должны следовать соглашениям текущего проекта.
- Описывай публичный API в OpenAPI-спецификации, если проект её использует.
- Не раскрывай внутреннюю структуру базы данных, классов и исключений.
- Не передавай stack trace, SQL, внутренние идентификаторы инфраструктуры и технические детали ошибок клиенту.
- Не делай API «универсальным» заранее. Один endpoint должен решать понятную пользовательскую или интеграционную задачу.

## URL и HTTP-методы

Используй существительные во множественном числе для коллекций ресурсов:

```text
GET    /api/v1/orders
GET    /api/v1/orders/{orderId}
POST   /api/v1/orders
PATCH  /api/v1/orders/{orderId}
DELETE /api/v1/orders/{orderId}
```

Не используй глаголы в URL, если операция естественно выражается HTTP-методом:

```text
Плохо: POST /api/v1/createOrder
Хорошо: POST /api/v1/orders
```

Для доменных действий, которые не являются обычным CRUD, используй явный action endpoint только при необходимости:

```text
POST /api/v1/orders/{orderId}/cancel
POST /api/v1/orders/{orderId}/confirm-payment
```

Правила:

- `GET` не должен изменять состояние.
- `POST` создаёт ресурс или запускает неидемпотентную операцию.
- `PUT` заменяет ресурс целиком и должен быть идемпотентным.
- `PATCH` частично изменяет ресурс.
- `DELETE` удаляет ресурс и должен быть идемпотентным с точки зрения желаемого конечного состояния.
- Не используй `GET` для операций, которые меняют данные.
- Не передавай чувствительные данные в query parameters.

## Именование полей

- Используй единый формат полей, принятый в проекте. По умолчанию — `camelCase`.
- Используй ясные доменные имена: `createdAt`, `updatedAt`, `customerId`, `totalAmount`.
- Не используй неочевидные сокращения: `usrId`, `amt`, `dt`.
- Идентификаторы именуй последовательно: `orderId`, `userId`.
- Временные значения передавай в ISO 8601 с timezone для timestamp:
  `2026-09-15T10:30:00Z`.
- Денежные значения не передавай в `float` или `double`; используй decimal-строку либо целое число в минимальных единицах согласно соглашению проекта.
- Enum-значения должны быть стабильными и документированными.

Пример ресурса:

```json
{
  "id": "ord_01J3X6MK9X1M7P7B8F3FZQ8B2H",
  "status": "PROCESSING",
  "createdAt": "2026-09-15T10:30:00Z",
  "updatedAt": "2026-09-15T10:35:12Z",
  "totalAmount": {
    "amount": "125.50",
    "currency": "EUR"
  }
}
```

## Request и response модели

Не используй одну и ту же DTO-модель для request, response, persistence и domain.

Разделяй:

- запрос на создание;
- запрос на частичное обновление;
- ответ API;
- внутреннюю доменную модель;
- JPA entity или persistence-модель.

Пример:

```json
POST /api/v1/orders

{
  "items": [
    {
      "productId": "prd_01J3X6MK9X1M7P7B8F3FZQ8B2H",
      "quantity": 2
    }
  ]
}
```

```json
201 Created

{
  "id": "ord_01J3X6MK9X1M7P7B8F3FZQ8B2H",
  "status": "NEW",
  "createdAt": "2026-09-15T10:30:00Z",
  "items": [
    {
      "productId": "prd_01J3X6MK9X1M7P7B8F3FZQ8B2H",
      "quantity": 2
    }
  ]
}
```

Не возвращай чувствительные поля:

- пароли и password hash;
- access token и refresh token, если они не являются явной частью авторизационного сценария;
- секреты интеграций;
- внутренние флаги безопасности;
- персональные данные, не нужные клиенту;
- технические поля persistence-уровня.

## HTTP status codes

Используй корректные статусы HTTP:

| Ситуация | Статус |
|---|---:|
| Успешное чтение или обновление | `200 OK` |
| Успешное создание ресурса | `201 Created` |
| Асинхронная операция принята | `202 Accepted` |
| Успешный запрос без тела ответа | `204 No Content` |
| Ошибка синтаксиса или структуры запроса | `400 Bad Request` |
| Пользователь не аутентифицирован | `401 Unauthorized` |
| Недостаточно прав | `403 Forbidden` |
| Ресурс не найден или намеренно скрыт | `404 Not Found` |
| Конфликт состояния или версии ресурса | `409 Conflict` |
| Ошибка бизнес-валидации | `422 Unprocessable Entity`, если этот стандарт принят в проекте |
| Превышен rate limit | `429 Too Many Requests` |
| Непредвиденная ошибка сервера | `500 Internal Server Error` |
| Временно недоступна зависимость | `503 Service Unavailable` |

Не возвращай `200 OK` с полем `success: false` для ошибок, которые корректно выражаются HTTP status code.

## Формат ошибок

Все endpoint-ы должны возвращать ошибки в едином формате.

Рекомендуемый формат:

```json
{
  "code": "VALIDATION_FAILED",
  "message": "Request validation failed.",
  "traceId": "4f7c3dc3c4f448c89b353c147b33772b",
  "violations": [
    {
      "field": "items[0].quantity",
      "code": "MIN_VALUE",
      "message": "Quantity must be greater than zero."
    }
  ]
}
```

Правила:

- `code` — стабильный машиночитаемый код ошибки.
- `message` — безопасное человекочитаемое описание.
- `traceId` — идентификатор запроса для диагностики, если он используется в проекте.
- `violations` — список ошибок полей для validation errors.
- Не включай stack trace в response.
- Не передавай внутренние исключения и SQL-сообщения.
- Не возвращай разные форматы ошибок для разных контроллеров.

## Валидация

Валидация выполняется на нескольких уровнях:

1. На границе HTTP API — структура, обязательность полей, формат, диапазоны.
2. В application/domain слое — бизнес-инварианты.
3. На уровне базы данных — ограничения целостности.

Не полагайся только на frontend-валидацию.

Правила:

- Отклоняй неизвестные поля в критичных API, если это совместимо с политикой проекта.
- Ограничивай размеры строк, массивов, вложенности и payload.
- Валидируй идентификаторы, даты, enum-значения, числовые диапазоны и связи между полями.
- Не выполняй необратимое действие до прохождения полной валидации.
- Ошибки валидации должны быть детерминированными и понятными клиенту.

## Фильтрация, сортировка и пагинация

Коллекции, которые потенциально могут быть большими, должны поддерживать ограничение выдачи.

Рекомендуемый формат offset pagination:

```text
GET /api/v1/orders?page=0&size=20&sort=createdAt,desc
```

Пример ответа:

```json
{
  "items": [
    {
      "id": "ord_01J3X6MK9X1M7P7B8F3FZQ8B2H",
      "status": "PROCESSING",
      "createdAt": "2026-09-15T10:30:00Z"
    }
  ],
  "page": {
    "number": 0,
    "size": 20,
    "totalElements": 125,
    "totalPages": 7
  }
}
```

Правила:

- Ограничивай максимальный `size` на сервере.
- Используй единый формат пагинации во всех API.
- Явно документируй поддерживаемые поля сортировки и фильтрации.
- Не позволяй клиенту сортировать по произвольному имени поля.
- Для больших и часто меняющихся коллекций рассмотри cursor pagination.
- Не возвращай всю таблицу или историю без ограничений.
- Проверяй, что пагинация и сортировка поддержаны индексами, когда это необходимо.

## Идемпотентность и повторные запросы

Для критичных операций создания, особенно связанных с оплатой, заказами или внешними интеграциями, поддерживай идемпотентность.

Рекомендуемый подход:

```text
Idempotency-Key: 3d506c65-98b7-4d1a-a5c0-6a3fce79864f
```

Правила:

- Один ключ идемпотентности должен быть связан с конкретной операцией и пользователем.
- Повторный запрос с тем же ключом и тем же payload должен вернуть предсказуемый результат.
- Повторный запрос с тем же ключом, но другим payload должен быть отклонён как конфликт.
- Политика хранения ключей и ответов должна быть ограничена по времени и документирована.
- Не реализуй автоматические retry на клиенте для неидемпотентных операций без соответствующей поддержки API.

## Версионирование и изменения контрактов

По умолчанию новые поля в response должны быть опциональными для потребителей, а новые поля в request — необязательными, если это возможно.

Считай breaking change следующими изменениями:

- удаление поля;
- переименование поля;
- изменение типа поля;
- изменение семантики значения;
- добавление обязательного request-поля;
- изменение формата ошибки;
- изменение URL или HTTP-метода;
- изменение авторизационных требований;
- изменение поведения пагинации, сортировки или фильтрации;
- изменение enum без проверки влияния на потребителей.

Для breaking change:

1. Предпочитай новую версию API.
2. Документируй период deprecation.
3. Предоставляй путь миграции.
4. Не удаляй старую версию до завершения согласованного периода поддержки.
5. Обновляй контрактные тесты и OpenAPI-описание.

## Безопасность API

- Все защищённые endpoint-ы должны требовать аутентификацию и проверку авторизации.
- Проверяй права доступа к конкретному ресурсу, а не только факт наличия роли.
- Не доверяй идентификатору пользователя из request body, query или path, если он должен определяться из authentication context.
- Применяй rate limit для чувствительных и дорогостоящих endpoint-ов.
- Устанавливай ограничения на размер тела запроса.
- Не передавай секреты в URL.
- Не кэшируй приватные ответы в общедоступных кэшах.
- Явно настраивай CORS, разрешая только необходимые origins, методы и заголовки.
- Не включай debug-информацию в production-ответы.

## Документация и контрактные тесты

Для каждого нового или изменённого публичного endpoint-а:

1. Обнови OpenAPI-спецификацию или принятую документацию.
2. Добавь описание авторизации.
3. Опиши request и response примеры.
4. Документируй возможные статусы и ошибки.
5. Добавь contract/integration тесты для критичных сценариев.
6. Проверь совместимость с существующими клиентами.
7. Укажи в финальном отчёте изменения контракта и риск breaking changes.
